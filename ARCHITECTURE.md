# Architecture decisions

## 1. Deliver vertical slices with explicit verification gates

The user requested independently verifiable milestones. Milestone 1 implements manual library management and persistence. Milestones 2, 3 and 4 were explicitly requested after the preceding automated gates passed, while the external native UI automation problem remained unresolved. That open review is retained in the status report. Source implementation, passing compilation and interactive verification are tracked separately.

## 2. SwiftData owns structured storage; the repository owns mutations

Versioned schemas define global Paper, Course and explicit CoursePaper entities. Association rows carry durable unique membership keys, course-specific notes and optional priority. UUIDs and a separate unique paper identity key prepare for version-independent arXiv identity without pretending that manually entered titles are unique identifiers.

V1 through V4 are frozen historical schemas. V2 adds optional course color and paper rating; V3 adds durable ImportJob rows, journal reference and a conservative metadata-edit protection flag. New imports clear that flag; manual source edits set it. Migrated records default to protected. V4 adds PDFDocumentRecord, PDFProcessingJob, PDFPageText and TextChunk. V5 adds AIAnalysis, AIProcessingJob, AnalysisProfile, Topic, PaperTopic and a manual-topic protection flag. Future schema changes must add a version and migration stage rather than edit historical schemas in place. Migration tests write actual V1/V2/V3/V4 stores and open them through the current V5 bootstrap, preserving identifiers, notes, author order, ratings, course context, import/PDF jobs, source text and reading position.

CoursePaper stores explicit UUID references rather than cascading relationships. The repository validates those references, prevents duplicate assignments and saves membership deletions together with the owning course/paper deletion. Deleting a course never deletes a Paper. Future models that refer to Paper must extend the same deletion transaction and tests.

All current structured-data mutations run on the main actor in one repository context, with autosave disabled and explicit save/rollback boundaries. Views do not write SwiftData properties directly. Metadata edits have an API that excludes user notes and reading state. Network retrieval, XML parsing, file verification, PDF extraction, chunking and model generation run through dedicated actors; each returned result is committed by the repository. No AI job is started by metadata import or PDF extraction.

## 3. Stable storage and fail-closed startup

Storage configuration depends on an explicit mode, never on `#if DEBUG`, the app bundle directory, or the build number. The shared Xcode scheme opts into demo mode via `--demo`; launching a normally installed app defaults to production. Test configuration accepts only a proper subdirectory of the resolved system temporary directory.

Bootstrap acquires an exclusive advisory process lock before touching the store. Before every existing-store open, it copies the closed Store directory, including SQLite/WAL/SHM and any sibling support files, to a pending snapshot, writes a versioned manifest and publishes it by a same-volume rename. Copy failure aborts startup before SwiftData opens. The lock remains owned by LibraryStore throughout the application session. All application store access must use this bootstrap; an external tool ignoring the advisory lock is outside that guarantee.

This initial conservative policy snapshots every reopen, including before migration, without silently deleting old snapshots. It trades disk usage/startup time for a simple recovery boundary. Snapshot retention, full disk accounting and portable versioned export/import are milestone 5 work. A snapshot includes structured PDF records and extracted text, but not PDF file bytes; it is not a portable library export and is not copied from an active SwiftData connection.

If migration or startup fails, no deletion, automatic reset or empty-store fallback runs. The original path stays in place and the pre-open snapshot remains available. SwiftData can attempt its own transactional migration at the original location; the closed-store snapshot preserves the pre-attempt bytes. Recovery is explicit and happens with all application processes closed.

## 4. Independently test the file-safety boundary

The initially available Command Line Tools included SwiftData interfaces but not Apple's SwiftData macro implementation. PaperLibrarySupport therefore contains the production Foundation-only configuration, locking, snapshots, errors and localized resources. The StorageChecks executable exercises this same code without a fake persistence replacement. It also spawns an actual SQLite writer, lets it exit with committed data in WAL, snapshots the now-closed store and reads the committed data from the copy.

These checks do not validate SwiftData migration or the SwiftUI interface. After full Xcode was installed, the eleven SwiftData/repository tests, including migration, passed under Swift Package Manager and Xcode. The project does not ship mock models, manually fabricated SwiftData macro expansions or a substitute database.

Verification scripts select an installed full Xcode for their own process when necessary, without changing the user's global `xcode-select` setting. Both native target configurations use `ONLY_ACTIVE_ARCH = YES` to match Swift package dependencies for the intended single-Mac installation. The app bundle is assembled in a staging directory with resource bundles under `Contents/Resources`, then signed and checked before publication to the generated build output.

## 5. Locality and UI

Milestone 1 creates no network clients, telemetry, cloud containers or AI sessions. All UI labels use Italian localization resources. Original paper content stays as entered. The native split view hosts a table and detail inspector, with confirmation before destructive deletions.

Notes are saved on each edit in the current slice. Failed writes retain the latest draft in application state across selection changes; retry is visible and normal termination attempts to save before allowing the process to exit. A later measured performance optimization may coalesce writes only if it adds a reliable flush mechanism for selection changes and termination.

Metadata, document records, job lists, profiles and topic labels currently load eagerly; the import history view displays pages of 100 rows. Analysis content, PDF page text and chunks are fetched on demand, never as part of startup reload; there are no vector payloads yet. The analysis interface fetches the latest 100 records for the selected paper. Performance at 5,000 papers has not been measured. Later search/indexing work must introduce appropriate batching and background processing before reporting large-library performance.

## 6. Bound arXiv and DOI retrieval

The import queue accepts a tagged arXiv or DOI identifier and routes each to its metadata provider. Existing import rows retain their canonical identifier/version representation; DOI rows use the normalized DOI and no version, requiring no schema migration. DOI imports call the fixed HTTPS Crossref work endpoint, with DataCite lookup after a Crossref 404. Pasted DOI URLs are parsed into identifiers rather than fetched directly. The ephemeral transport rejects redirects, cookies and credentials, bounds advertised and streamed responses to 2 MiB, and limits transient retries. Requests are paced and server `Retry-After` is honored.

DOI metadata must match the requested DOI and contain a title. Authors, dates and abstracts may be absent; markup is converted to plain text, and partial refreshes preserve previously retrieved optional fields. Case-insensitive DOI matching reuses existing DOI, manual or arXiv papers while retaining annotations and protecting manually edited metadata. arXiv records with distinct IDs remain distinct even if they share a DOI. DOI references open the publisher through the system browser; PDF downloads continue to use the arXiv-only policy below.

The arXiv provider accepts validated arXiv identifiers only and constructs its own `id_list` request to the fixed HTTPS API endpoint. It does not fetch arbitrary pasted URLs. Atom parsing validates namespaces, ordered authors, dates, required fields and PDF link identity. DTD/entity declarations are rejected, external entity resolution is disabled, and both advertised and streamed response sizes are bounded. Publisher links are ignored; metadata import stores pinned HTTPS arXiv references without downloading them.

The [arXiv API terms](https://info.arxiv.org/help/api/tou.html) require at most one legacy request every three seconds and one connection at a time. A scheduler serializes metadata and PDF calls, including retries, and conservatively waits at least three seconds after completion before the next request. Its generic `perform` operation retains the permit for the complete streamed PDF transfer. Production and demo use the same advisory file lease and persisted deadline in a separate application-specific network folder. The lease covers the request, and every permit holder rereads the deadline before sending. Test configurations never touch this global state.

An ephemeral URLSession disables application cookies, credentials and caching, applies timeouts, and rejects redirects. Transient errors are retried at most twice after the initial attempt, with backoff and server `Retry-After` respected. Cooldowns longer than 60 seconds are persisted and reported for later retry. The HTTPS endpoint was checked with a real request; parameter/version semantics follow the [official user manual](https://info.arxiv.org/help/api/user-manual.html).

## 7. Durable import ownership and idempotent commits

ApplicationState owns one ImportCoordinator; the dialog only observes it. Pasted inputs are validated/deduplicated by exact identifier/version before creating a durable batch. Invalid inputs become failed jobs, not hidden omissions. Each batch has an ID, and each job retains source input, requested version, destination/options, timestamps, processing-attempt count, progress, outcome and error state.

The coordinator processes up to twenty jobs from one batch at a time. Existing global records can complete without a request, with optional idempotent course assignment. New metadata or an explicitly requested refresh is saved with the successful job state in one repository commit. Refresh never alters global notes, reading state, favorite, rating or protected metadata. Changing source versions does not change an already downloaded document; PDF versions are separate V4 records.

Cancellation changes only pending/in-progress jobs. A late response cannot commit a cancelled job, completed papers remain saved, and other queued batches continue. Normal termination saves interrupted states before cancelling the worker. On startup, leftover pending/in-progress jobs become interrupted and require explicit user retry. Closing a dialog does not terminate the worker; terminating the application does.

The request-attempt count in the HTTP service and the persisted processing-attempt count on an import job have different meanings. One processing attempt may include bounded HTTP retries. A deleted destination produces an atomic job failure; retry can choose another destination. Deleting a paper clears historical job links and cancels outstanding jobs for that logical paper to avoid reimporting it as a side effect of its deletion.

## 8. Immutable PDF files and recoverable processing

ApplicationState owns one PDFCoordinator and its serial worker. Download and extraction are separately persisted jobs; metadata is already committed before either begins. Pending/in-progress work becomes interrupted when reopening or quitting and requires explicit retry. Downloads restart rather than using byte ranges. Late cancelled responses cannot commit document records. Repeated active operations deduplicate by paper, version and operation.

PDFSourcePolicy constructs a version-pinned `https://arxiv.org/pdf/…` URL from validated source identity. The ephemeral transport rejects redirects and other hosts, streams bounded buffers into `PDFs/.staging/<job-UUID>.part`, reserves free disk space and reports throttled durable progress. PDFFileStore validates regular files, safe parent directories, signature, size, checksum and PDFKit readability before an atomic move to `PDFs/<paper-UUID>/vN-<SHA-256>.pdf`. Existing content is never overwritten. Verified records can complete without networking; modified bytes produce an error before a request. Finder reveal remains available for preserving an external edit.

The filesystem and SwiftData do not share one transaction. A complete validated file is published first; the record, completed download job and pending extraction job are then saved together. A crash in that gap can leave an unreferenced complete file, which is preserved. Startup maintenance removes only owned stale partials. Deletion uses the reverse safety boundary: a saved tombstone removes the document from active records, deletes page/chunk data and cancels related work before physical deletion. Tombstones allow failed physical removal to be retried. Deleting a paper follows the same protocol while retaining courses.

PDFTextExtractor owns a worker PDFDocument and returns Sendable page DTOs. It checks cancellation between pages and bounds pages, total text and text per page. PDFKit can allocate internally while parsing; these are application processing limits, not a hard memory sandbox. Conservative normalization removes repeated short edge lines only across sufficiently many multi-line pages. Page-local chunks have overlap, exact one-based source pages, content hashes, index version and stable IDs. Re-extraction replaces page/chunk rows atomically; extraction failure preserves the readable file. `chunksReady` means stored text, without embeddings or AI.

## 9. Native PDFKit isolation and action policy

The main-actor PDFReaderSession owns the one active UI PDFView, search selections and observation tokens. Closing cancels search and releases the document. A worker extraction document can coexist transiently; the app does not keep every PDF loaded. Page changes persist the position; search is asynchronous with a 500-character query and 1,000 retained matches. Contents traversal is bounded to 500 nodes and twelve levels.

LocalPDFView permits only GoTo actions targeting its own document. URL, remote-document and print delegate callbacks do nothing; extracted document text never triggers commands or network operations. A separate retained NSObject delegate is essential: making PDFView its own delegate caused recursion in PDFKit's default scale callback. The actual reader test exercises opening/autoscaling as well as navigation, restored position, asynchronous search and document release, and guards against that regression.

PDFKit/Foundation search notifications contain non-Sendable selections. Observers explicitly use `queue: .main`; a narrow `nonisolated(unsafe)` notification binding is consumed immediately inside `MainActor.assumeIsolated`, without crossing tasks or retaining the notification. Views access all PDFKit UI objects on the main actor. The worker extractor uses its own actor-owned document.

## 10. Explicit on-device inference and bounded guided output

AppleAnalysisModel owns an explicit `SystemLanguageModel.default`; every LanguageModelSession names that model and supplies an empty tool list. No remote provider, Private Cloud Compute model, remote executor, AI network client or inference entitlement is configured. The provider rechecks actual availability and locale support before each generation. Unknown SDK availability reasons remain unknown instead of being mapped to invented download/device diagnoses. Non-AI operations do not depend on model readiness.

The installed SDK was inspected and a minimal @Generable probe compiled before integration. The runtime reported availability for Italian and English and an 8,192-token context on this Mac; code reads contextSize rather than assuming a fixed size. On macOS 26.4+, token counts include trusted instructions, the exact prompt and guided schema, with 1,400 output tokens and a 384-token reserve. Earlier supported systems use an estimate and the same bounded splitting/error path. Every model call uses a fresh session.

Untrusted source material is encoded into the prompt; it is never interpolated into trusted instructions or registered as a tool. Configurable profile objectives are authored by the user, bounded to 1,600 characters and recorded with each analysis. The three initial profiles have stable IDs and are seeded idempotently without resetting edits. The model selects numbered source passages through private @Generable types; the application resolves those IDs and copies original text into the persisted AnalysisOutput. Unknown IDs, invalid structures and literal numeric values absent from their cited passage are rejected. This avoids depending on the model to reproduce exact quotations. A local language recognizer rejects a confidently detected opposite Italian/English language in outputs of sufficient length; it is a heuristic, not a proof of language correctness.

The first real-model checks exposed omitted summaries, wrong-language output and quotation/schema delimiters copied into evidence. The final guided schema makes the summary required, explicitly states the output language and replaces free-form quotation generation with source-reference selection. Production code does not log source text or personal notes. The opt-in integration executable logs synthetic fixture outputs only.

AnalysisPipeline processes at most 64 source parts, with a maximum 160 excerpt-generation calls and six split levels for context failures. Abstract input is capped at 192,000 characters. PDF snapshots fetch at most 65 chunks to detect truncation and analyze the first 64; coverage is incomplete when more exist or extraction was incomplete. Intermediate outputs are validated against their source part. The reducer selects up to twelve distinct representative facts across fields and makes a separate bounded synthesis call, shrinking candidates on context errors. Final citations are resolved again against the original source parts and retain one-based PDF pages. Summarization is selective; matching a source passage does not establish semantic entailment or scientific correctness. The interface exposes evidence and separates hypothetical review questions from author claims.

## 11. Durable AI ownership and user-edit preservation

ApplicationState owns one serial AnalysisCoordinator, independent of the inspector and reader lifetimes. A paper has at most one pending/in-progress analysis job. Model absence and failures remain durable failed jobs with explicit retry; quitting or reopening converts unfinished work to interrupted before cancellation. Startup performs no inference. Retry creates a new attempt using the current source and selected profile version. Intermediate generations are not persisted; interrupted analysis restarts rather than claiming a resumable model session.

AIProcessingJob snapshots source kind/hash/PDF version, language, profile name/objective, prompt version and the previous matching analysis revision. Completion requires the same source fingerprint and unchanged previous revision. Analysis creation, suggested-topic assignment and job completion commit atomically. Notes, manual metadata and reading state are excluded from inference mutations. Analysis records store the explicit model API identifier and OS version; no unavailable model build identifier is invented.

Regeneration appends history rather than overwriting a record. Explicit personal corrections live beside the original structured output and evidence, set userEdited and increment the revision. Confirmation is required before generating after a matching edited analysis. A revision change while the worker is running rejects its late result. Per-paper manual topics set a protection flag; subsequent analyses retain their suggestions in history without replacing those chosen topics. Topic normalization only folds case/diacritics and whitespace; it does not merge distinct scientific concepts.

Paper deletion removes analyses and topic memberships and cancels active AI jobs in the same repository transaction, while retaining courses. PDF removal cancels dependent work and removes extracted text but preserves analysis history and provenance. User-facing source availability remains necessary to navigate historical page references. Default settings are local preferences; portable preservation of settings and complete library export remains milestone 5 work.

Apple's [context management](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window), [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel) and [guided-output safety](https://developer.apple.com/documentation/foundationmodels/improving-the-safety-of-generative-model-output) documentation informed this integration. SDK availability annotations, compiled code and actual runtime checks determine which APIs are used.

## 12. One persistent application bundle

The user requested a single current app and prevention of duplicate installed builds. The canonical artifact remains `build/release/Paper Library.app`. Both packaging configurations publish to that one path; the packaging default is Release. Both native Xcode configurations set `TARGET_BUILD_DIR` to `PAPERLIBRARY_APP_OUTPUT_DIR`, whose default is the same canonical directory, and use the fixed wrapper name `Paper Library.app`. The configuration's common products directory stays unchanged so Swift package modules and resource bundles remain discoverable. Generated product references and the shared scheme use the fixed app name. Xcode's default Derived Data choice therefore does not create another application product.

The verification script overrides only `PAPERLIBRARY_APP_OUTPUT_DIR` with a unique temporary product directory. It unregisters that temporary app and removes the directory on exit, including failures and handled signals. Compiler intermediates and test results remain cached, while the canonical signed app is preserved. Configuration validation asserts the fixed output policy; a separate inventory check rejects unexpected application bundles in the workspace and this project's default Derived Data folders. The packaging script also performs the inventory check after publication.

This policy governs builds from this project and its scripts. It does not monitor arbitrary user-made copies, externally restored archives or unrelated installation tools. No library/database path depends on the build output, and cleanup never targets Application Support or user papers. The two existing duplicate 0.4.0 Xcode products were unregistered and moved to the system Trash.

## 13. Stable native table geometry during imports

The native table previously let title cells vary between one and two lines. A fixture using the actual SwiftUI table and repository/import coordinator measured 24-point and 40-point rows after live insertion. The user reported overlapping row content until navigating away and back. The 0.4.1 fix used equal 44-point content frames and uniform 52-point native rows. In 0.4.2 the same geometry policy uses 62-point content frames and uniform 70-point native rows, with two title lines and a caption author line in one column. PDF/favorite indicators share that column. Data, selection bindings and sort state continue updating without resetting the table identity.

The reusable LibraryPaperTable lives in the PaperLibraryUI package target so the app and regression test instantiate the same view. Context menus and library actions remain in LibraryView. The test creates an offscreen NSHostingView/NSTableView using a temporary SwiftData library and an injected metadata provider; no production app or data is opened. It checks cell bounds, consistent row heights, incremental imports, metadata changes, resizing and deletion, plus retained table identity, selection and a resized column width. The pre-fix implementation fails these layout checks and the corrected view passes. This is native layout verification, not a claim of a complete interactive UI review.


## 14. Focused reading interface and multiple evidence references (0.4.2)

The toolbar consolidates entry methods and history into one plus menu. Filters are a menu, Favorites is a sidebar scope, and the inspector appears for a selection. Details, Notes and Summary are separate segmented views; paper identity resets per-paper presentation state. Metadata/course membership and PDF maintenance remain accessible in menus. Import presents entry and activity separately. The reader gives the PDF its full width until the notes/summary panel is requested. Settings hides database paths, schema versions and limits under Advanced.

The private guided schema selects 1–4 evidence IDs before each statement. AnalysisPoint and GroundedSummary accept optional supportingQuotes; older JSON without that field still decodes. This extends stored JSON, not the SwiftData schema. Each quote is checked independently against an original source part, then all numeric literals in a statement must occur among its cited passages. A point can therefore have multiple AnalysisCitation entries with the same pointIndex and different source pages. The reducer preserves every supporting quote rather than discarding all except the first. The interface displays every saved reference. This validation does not prove semantic entailment.

AppleAnalysisModel performs at most two fresh-session attempts for a source-validation failure. The second prompt requests valid references and shorter supported statements; cancellation is checked between attempts. No invalid output is saved, no cloud fallback is introduced, and the library coordinator retains its durable failure/retry behavior. The context headroom also covers the short repair instruction.
